# Local development setup

The hosted app is at <https://strength-training-app-six.vercel.app>. Use these instructions to develop a separate local copy. Local credentials and browser data are independent of the hosted app.

## Prerequisites and dependencies

Use Node.js 22.x, npm, PostgreSQL 17 server/client tools, and Git. On macOS with Homebrew PostgreSQL 17 installed, expose its tools in the current terminal:

```sh
export PATH="$(brew --prefix postgresql@17)/bin:$PATH"
node --version
pg_config --version
```

From a fresh clone's root:

```sh
npm --prefix backend ci
npm --prefix frontend ci
```

No root-level `npm install` is needed. The two packages have their own lockfiles.

## Create a development database once

If the project's existing PostgreSQL instance and `strength_training` database are available, reuse them and skip initialization. Never replace an existing `.local/postgres` directory to restart it.

For a **fresh clone** on macOS, the following creates a dedicated cluster on loopback port 5434. Run it from the repository root, as your normal Mac user:

```sh
mkdir -p .local
initdb -D .local/postgres --username="$USER" --auth-local=trust --auth-host=scram-sha-256
pg_ctl -D .local/postgres -l .local/postgres.log -o "-h 127.0.0.1 -p 5434 -k /tmp" start
createuser --host=/tmp --port=5434 --username="$USER" --pwprompt strength_app
createdb --host=/tmp --port=5434 --username="$USER" --owner=strength_app strength_training
```

Choose a local password at the prompt; you will put it in the ignored backend environment file. The app role owns this development database and is not a PostgreSQL superuser. Local administration uses a Unix socket; TCP connections require a password and bind to loopback. This recipe is for your development machine, not a public database server.

If port 5434 is already in use by your project, check `pg_ctl -D .local/postgres status` and reuse it. If another PostgreSQL installation uses a different port or admin account, create the app role/database there and match those settings in `.env` instead.

The PostgreSQL references describe [cluster initialization](https://www.postgresql.org/docs/17/app-initdb.html), [server control](https://www.postgresql.org/docs/17/app-pg-ctl.html), [role creation](https://www.postgresql.org/docs/17/app-createuser.html), and [database creation](https://www.postgresql.org/docs/17/app-createdb.html).

## Configure the backend and migrate

```sh
cd backend
npm run setup
```

This creates `backend/.env` from the example when needed, generates a private authentication secret, and configures exact localhost and Mac/phone origins. Existing database values are preserved. It does not create or start PostgreSQL.

Edit the generated `.env` in your editor. For the dedicated cluster above, keep `PGHOST=127.0.0.1`, `PGPORT=5434`, `PGDATABASE=strength_training`, and `PGUSER=strength_app`; replace `PGPASSWORD` with the password you chose. Do not commit this file.

| Variable | Local responsibility |
| --- | --- |
| `PORT` | API listener, normally 4001 |
| `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD` | Development PostgreSQL connection |
| `BETTER_AUTH_SECRET` | Private auth secret generated by setup |
| `APP_ORIGINS` | Exact allowed browser origins generated by setup |
| `DATABASE_URL` | Optional URL that takes precedence over the `PG*` settings; leave unset for the local recipe |
| `NODE_ENV` | Leave unset or use development locally; production requires hosted PostgreSQL and HTTPS origins |

Shell environment variables take precedence over `.env`. Use a development terminal without production `DATABASE_URL` or `NODE_ENV` overrides.

```sh
npm run db:migrate
npm run typecheck
npm run build
```

Expected: migrations are up to date and TypeScript succeeds. Migration reruns preserve data; changing an already-applied SQL migration is rejected by its checksum. Add a new migration instead.

## Start the app

In the backend terminal, leave this running:

```sh
npm run dev
```

In a second terminal, from the repository root:

```sh
cd frontend
npm run dev
```

Open <http://localhost:5173/>. Keep both terminals running for accounts and sync. Without the API, local logging remains usable, but accounts and server synchronization are unavailable.

| Port | Purpose |
| --- | --- |
| 5173 | Frontend development or explicitly configured production preview |
| 4001 | Loopback Express API |
| 5434 | Dedicated local PostgreSQL in this recipe |
| 5080 / 5443 | Optional local iPhone setup / HTTPS preview |

Stop frontend/backend foreground processes with Control+C in their own terminals. From the repository root, stop only the project database with `pg_ctl -D .local/postgres -m fast stop`. Restart that existing cluster with `pg_ctl -D .local/postgres -l .local/postgres.log start`.

## Test offline reopening locally

Stop the frontend dev process first so port 5173 is free, then:

```sh
cd frontend
npm run build
npm run preview -- --host localhost --port 5173 --strictPort
```

Open the exact same localhost address and wait for **Ready for offline use**. Save a set, stop this preview, and reopen the same address. The cached app and logged sets should remain. Restart the preview/API before testing account synchronization again. Vite development hot reload intentionally does not install the offline worker.

For local phone development, `npm run phone` in `frontend/` prints setup/HTTPS addresses and manages an ignored local test certificate. The Mac and phone must share Wi-Fi; the API/database must run for accounts. Follow the printed setup page and [local iPhone test guide](day-14.md). The hosted app uses normal HTTPS and does not need this certificate setup.

## Verification commands

From the repository root:

```sh
npm --prefix frontend test
npm --prefix frontend run lint
npm --prefix frontend run build
npm --prefix backend run typecheck
npm --prefix backend run build
npm --prefix backend test
```

A standalone backend test run skips its database integration cases unless `TEST_DATABASE_URL` is supplied. Prefer the [complete isolated suite](day-22.md), which provisions a temporary database and runs both browser engines:

```sh
cd frontend
npm run test:e2e:install
npm run test:e2e
```

## Troubleshooting

| Symptom | Check |
| --- | --- |
| Site unavailable on localhost | Start the frontend; use its printed address and leave the terminal running. |
| Account service unavailable | Start PostgreSQL and the backend; confirm `.env` values and migration success. The workout remains local. |
| Database connection refused | Check the database process and port. The template uses 5434, not a system service's possible 5432. |
| Password authentication failed | Match the app role's password in the ignored `.env`; do not regenerate or delete database data. |
| Request host/origin rejected | Use an exact `APP_ORIGINS` address. If you change the frontend port, add that origin and restart the backend. |
| Port already in use | Reuse the verified server or stop it in its own terminal. Do not start a second preview on the same ports. |
| Old phone app files | Save drafts, close other workout tabs, and reopen. For the Mac HTTPS preview, `/api/app-update` can refresh files without clearing saved data. |
| Workouts absent on another address | IndexedDB belongs to the origin. Use the original address or sign into the same server account and enable sync for that device. |

Production secrets, hosted migrations, and manual releases are covered in [deployment](day-24.md). Do not use hosted credentials for disposable tests or put them in frontend `VITE_*` variables.
